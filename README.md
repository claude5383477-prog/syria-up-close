# سوريا عن قرب | Syria Up Close

دليل سفر مستقل عن سوريا، بالعربية أولاً ثم الإنجليزية، مع لوحة تحرير وصفحة خفيفة للمراسلين على الأرض.
المواصفات المعتمدة في [`SPEC.md`](SPEC.md)، والمهام في [`PLAN.md`](PLAN.md)، وعقد الجودة في [`CONSTRAINTS.md`](CONSTRAINTS.md).

- الموقع العام: Next.js 16 (App Router)، ويُعاد توليد الصفحات كل ساعة وعند كل نشر.
- لوحة التحرير: Payload CMS 3 على `/admin`.
- صفحة المراسل: `/correspondent`، وحجمها أقل من 150KB على الهاتف.
- قاعدة البيانات: PostgreSQL.
- الصور: Vercel Blob في الإنتاج، أو تخزين متوافق مع S3 مثل Cloudflare R2 إن ضُبط `S3_BUCKET`، أو القرص المحلي (`MEDIA_DIR`).

## المتطلبات

- Node.js 24 (انظر `.nvmrc`).
- لا تحتاج Docker ولا PostgreSQL مثبتاً للتطوير: `npm run db` يشغّل قاعدة مضمّنة (embedded-postgres).
- Python 3 فقط إن أردت إعادة قصّ الخط (`npm run fonts:subset`). ملفات الخط الناتجة محفوظة في المستودع.

## التشغيل المحلي

```bash
npm ci
cp .env.example .env
```

املأ `PAYLOAD_SECRET` وحسابات الـ seed في `.env`، ثم شغّل القاعدة في نافذة طرفية مستقلة واتركها تعمل:

```bash
npm run db
```

وفي نافذة أخرى:

```bash
npm run migrate
npm run seed
npm run dev
```

- الموقع: <http://localhost:3000>، والإنجليزية على `/en`.
- اللوحة: <http://localhost:3000/admin>.
- صفحة المراسل: <http://localhost:3000/correspondent/login>.

أي تغيير في نموذج البيانات يحتاج migration تُحفظ في المستودع:

```bash
npm run migrate:create -- اسم-التغيير
```

## النشر بـ Docker على خادم واحد

الصورة تُبنى **دون قاعدة بيانات**. عند الإقلاع تجري ثلاث خطوات:

1. تطبّق الـ migrations (`payload migrate`).
2. تشغّل الخادم.
3. تحدّث كل الصفحات العامة من القاعدة (`scripts/docker/start.mjs`).

لذلك يعمل البناء على أي منصة، حتى التي لا تصل إلى القاعدة أثناء البناء.

على الخادم، وفيه Docker مع Compose:

```bash
cp .env.example .env
```

املأ في `.env`:

- `PAYLOAD_SECRET`: سلسلة عشوائية طويلة، مثلاً `openssl rand -hex 32`.
- `NEXT_PUBLIC_SITE_URL`: رابط الموقع النهائي بلا `/` في آخره. يُثبَّت داخل الصورة، فأعد البناء إن غيّرته.
- `POSTGRES_PASSWORD`.
- حسابات الـ seed بكلمات مرور قوية.

ثم:

```bash
docker compose up -d --build
```

أول مرة فقط، أدخل المحتوى الأولي ثم حدّث الصفحات لتظهر فوراً:

```bash
docker compose exec app npm run seed
```

```bash
docker compose exec app npm run revalidate
```

- البيانات في volume `pgdata`، والصور في volume `media`، وتبقيان بعد إعادة البناء.
- الموقع على المنفذ `APP_PORT` (افتراضياً 3000). ضع أمامه خادماً عكسياً بشهادة HTTPS، مثل Caddy أو Nginx.
- كل `docker compose up -d --build` لاحق يطبّق أي migration جديدة تلقائياً عند الإقلاع.

> **حالة التحقق:** Docker غير مثبت على جهاز التطوير، لذلك لم تُبنَ الصورة فعلياً بعد. ما جُرّب حتى الآن، على Windows دون Docker:
> - مرحلة البناء نفسها على نسخة مطابقة لسياق Docker.
> - الإقلاع الكامل على قاعدة جديدة: migrate، ثم seed، ثم `start.mjs`. أظهر المحتوى الحقيقي بعد التحديث.
>
> يُختبر `Dockerfile` كاملاً عبر بناء منصة النشر بعد اختيارها.

## الاستضافة: Vercel Hobby وNeon وVercel Blob (قرار 2026-10-18)

الموقع مستضاف مجاناً على ثلاث خدمات:

- **Vercel (Hobby):** الموقع واللوحة، المشروع `abdullah-98df/syria-up-close`، في منطقة `fra1`.
- **Neon (الخطة المجانية):** قاعدة البيانات.
  - الإنتاج: المشروع `syria-up-close-prod` (`patient-wildflower-66185499`) في `aws-eu-central-1`، الفرع `production`، Postgres 18.
  - التطوير والاختبار والمعاينة (Preview): المشروع القديم في أوهايو (Ohio). هذا يُبقي حصة الحوسبة المجانية للإنتاج وحده.
- **Vercel Blob (المجاني):** الصور، في المخزن العام `syria-up-close-blob` (`fra1`) المربوط بالمشروع. أضاف Vercel المتغير `BLOB_READ_WRITE_TOKEN` إلى Production وPreview تلقائياً، فلا مفاتيح تُنسخ يدوياً.

كل نشر على `main` يذهب إلى الإنتاج، وأي فرع آخر يصبح Preview. أمر البناء (`npm run vercel-build` في `vercel.json`) ينفّذ:

1. المهاجرات على الاتصال المباشر.
2. بناء الصفحات من بيانات الفرع نفسه.

إن فشلت مهاجرة فشل النشر كله، ويبقى الإصدار السابق يعمل.

### أين تُحفظ الصور

يختار الكود مكان التخزين من المتغيرات وحدها، دون تعديل كود (`src/lib/storage.ts`):

| الشرط | التخزين | أين يُستخدم |
|---|---|---|
| `BLOB_READ_WRITE_TOKEN` موجود | Vercel Blob | الإنتاج والمعاينة |
| `S3_BUCKET` موجود، ولا يوجد رمز Blob | S3 أو Cloudflare R2 | للانتقال لاحقاً |
| لا هذا ولا ذاك | القرص المحلي (`MEDIA_DIR`) | التطوير وصورة Docker |

- في Blob تُعرض الصور مباشرة من شبكة Blob العامة، لا عبر دالة.
- **لا رفع مباشر من المتصفح إلى المخزن:** كل صورة تمر عبر Payload، فتُعاد ترميز الأصل وكل مقاس بـ sharp وتُزال كل البيانات الوصفية (EXIF وGPS ونوع الجهاز). هذا لحماية المراسلين، لأن الرفع المباشر كان يخزّن الأصل الخام كما هو.
- **حد الحجم والأنواع:** كل صورة حدها 4MB (للمحررين والمراسلين، على الخادم)، وتُصغَّر الأكبر قبل الرفع. الأنواع المقبولة JPEG وPNG وWebP وAVIF فقط، تُفحص من محتوى الملف لا من اسمه، فيُرفض SVG وأي HTML متنكّر.
- صور المراسلين تُضغط في المتصفح أولاً (حدها 3MB)، ثم ترفعها الدالة.

### إعداد Neon

1. **مشروع الإنتاج:** `syria-up-close-prod` في AWS Frankfurt (`aws-eu-central-1`).
   - أنشأه Neon بـ Postgres 18، بينما التطوير المحلي على 17.
2. **اسم الفرع:** إن كان الفرع الافتراضي باسم `main`، أعد تسميته إلى `production`.
3. **حجم الحوسبة:** في فرع `production` ← **Computes** ← **Edit**، اجعل الحجم الأدنى والأعلى 0.25 CU. التوقف بعد 5 دقائق خمول ثابت في الخطة المجانية.
4. **فرع المعاينة:** في مشروع أوهايو أنشئ فرعاً باسم `preview`، واجعل حجمه 0.25 CU أيضاً.
5. **لا تفعّل تكامل Neon مع Vercel:** إنه ينشئ متغيراته وفروعه بنفسه. نُدخل المتغيرات كما في الجدول أدناه.

لكل فرع سلسلتا اتصال، من **Connect** أو من `neonctl connection-string`:

- **مع** pooling (`--pooled`): هذه `DATABASE_URL`.
- **بدون** pooling: هذه `DATABASE_URL_UNPOOLED`.

يجب أن تكون السلسلتان للفرع نفسه، وإلا رفض البناء أن يعمل.

### متغيرات Vercel

من **Project** ← **Settings** ← **Environment Variables**، أو عبر `vercel env add`. فعّل **Sensitive** للأسرار.

| المتغير | Production | Preview | من أين |
|---|---|---|---|
| `DATABASE_URL` 🔒 | فرع `production` في `syria-up-close-prod`، **مع** pooling | فرع `preview` في مشروع أوهايو، **مع** pooling | Neon |
| `DATABASE_URL_UNPOOLED` 🔒 | الفرع نفسه، **بدون** pooling | الفرع نفسه، **بدون** pooling | Neon |
| `PAYLOAD_SECRET` 🔒 | قيمة عشوائية: `openssl rand -hex 32` | قيمة مختلفة | تولّدها أنت |
| `NEXT_PUBLIC_SITE_URL` | رابط الإنتاج، ثم النطاق لاحقاً | **لا تضعه**: المعاينة تستخدم عنوانها تلقائياً | Vercel ← Domains |
| `BLOB_READ_WRITE_TOKEN` 🔒 | يضيفه Vercel تلقائياً | يضيفه Vercel تلقائياً | ربط مخزن Blob |
| `S3_*` و`R2_PUBLIC_URL` | **لا تضعها** ما دام Blob مستخدماً | — | للانتقال إلى R2 لاحقاً |

إعدادات المشروع في Vercel:

- **Node.js Version:** 24.x، من **Settings** ← **Build and Deployment**.
- **Framework:** Next.js.
- **أمر البناء والمنطقة:** يأتيان من `vercel.json`، فلا تغيّرهما.

**لا** توضع `SEED_*` في Vercel؛ لا تلزم إلا للـ seed من الجهاز.

### الانتقال لاحقاً إلى Cloudflare R2

هذا الدعم باقٍ في الكود. إن احتجناه:

1. أنشئ bucket ومفتاح وصول (Object Read & Write) في R2.
2. اضبط سياسة CORS لتسمح بـ `PUT` و`GET` وبالترويسات `content-type` و`if-none-match` من رابط الموقع.
3. ضع `S3_BUCKET` و`S3_ENDPOINT` (`https://<ACCOUNT_ID>.r2.cloudflarestorage.com`) و`S3_REGION=auto` والمفتاحين في Vercel.
4. افصل مخزن Blob عن المشروع، حتى يختفي `BLOB_READ_WRITE_TOKEN`، ثم أعد النشر.
5. للعرض من نطاق R2 العام مباشرة: ضع `R2_PUBLIC_URL`.

الصور القديمة في Blob لا تُنقل تلقائياً.

### الـ seed على الإنتاج (مرة واحدة)

أنشئ على جهازك ملف `.env.production.local`، وهو مستثنى من git، وفيه:

- `DATABASE_URL` و`DATABASE_URL_UNPOOLED` لفرع `production`.
- `PAYLOAD_SECRET` نفسه الموجود في Vercel.
- `NEXT_PUBLIC_SITE_URL`.
- `SEED_*` بكلمات مرور قوية.

لا يحوي هذا الملف أي `S3_*`، لأن الإنتاج على Blob.

رمز Blob يُسحب إلى ملف منفصل، مستثنى من git أيضاً، دون طباعته:

```bash
npx vercel env pull .env.blob.local --environment=production
```

(ثم يُترك فيه `BLOB_READ_WRITE_TOKEN` وحده.)

ثم:

```bash
npm run seed:remote -- .env.production.local .env.blob.local
```

السكربت لا يطبع أي قيمة، ويرفض العمل إذا:

- نقص متغير؛
- أو كانت القاعدة محلية؛
- أو اختلف الفرعان.

بعد الـ seed يحدّث صفحات الموقع المنشور. القياس بعدها:

```bash
npm run lhci -- https://<اسم-المشروع>.vercel.app
```

## حد محاولات الدخول (Vercel WAF)

حسب [وثائق Vercel](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting) (آخر تحديث 2026-08-28):

- **Hobby:** قاعدة حد معدل **واحدة** لكل مشروع، بنافذة ثابتة بين 10 ثوانٍ و10 دقائق.
- **مفتاح العدّ:** IP أو JA4.

فقاعدة واحدة تغطي مسارات الدخول كلها. هذا يضاف إلى قفل Payload لكل حساب بعد 5 محاولات خاطئة مدة 15 دقيقة.

1. لوحة Vercel ← مشروع `syria-up-close` ← **Firewall** في الشريط الجانبي.
2. **Configure** (أعلى اليمين) ← **+ New Rule**.
3. **Name:** `login-rate-limit`.
4. شروط **If** (يجب أن تتحقق كلها):
   - **Request Method** ← **Equals** ← `POST`.
   - **Request Path** ← **Matches expression** (regex) ← `^/(api/users/(login|forgot-password|unlock)|correspondent/login)$`.
5. **Then:** **Rate Limit**. في أول مرة تظهر نافذة **Rate Limiting Pricing**: راجعها ثم **Continue**.
6. الإعدادات:
   - **Algorithm:** Fixed Window.
   - **Time Window:** `60s`.
   - **Request Limit:** `10`.
   - **Key:** IP.
   - **Action:** Default (429).
7. **Save Rule** ← **Review Changes** ← **Publish**.
8. للتحقق: في نظرة Firewall العامة اختر القاعدة من قائمة تجميع حركة المرور وراقب الطلبات المطابقة.

ملاحظات:

- **إن لم يظهر خيار regex:** قاعدة واحدة لا تكفي للمسارين معاً؛ أخبر المطوّر لاختيار بديل.
- **الشبكة المشتركة:** مراسلون كثيرون قد يخرجون من IP واحد عند مزوّد الاتصال (CGNAT)، و10 طلبات في الدقيقة تكفي لدخول عادي من عدة أشخاص. إن ظهر رفض لدخول مشروع، ابدأ بإجراء **Log** يوماً لمراقبة الأثر، ثم ارجع إلى 429.

## صور المراسلين: خاصة حتى النشر

- صورة يرفعها المراسل لا يراها إلا هو والطاقم (المحررون والمدير)، حتى تُنشر.
- تصبح عامة تلقائياً حين ينشر محرر شيئاً يستخدمها: تقرير موسم، أو مدينة، أو مكان، أو قصة، أو تفصيلة يوم، أو إقامة.
- تبقى خاصة ما دام ما يستخدمها مسودة.
- صور الطاقم عامة فور رفعها.
- يمكن للمحرر أيضاً تعليم «منشورة للعامة» في الشريط الجانبي للصورة يدوياً. المراسل لا يستطيع تغيير هذا الخيار.
- سجل النسخ (versions) يتبع القاعدة نفسها: المراسل لا يرى إلا نسخ تقاريره ومدنه.
- كل صورة تُرفع (من `/correspondent` أو `/admin`) تُحفظ باسم عشوائي (UUID)، لا باسم ملف الهاتف، فلا يمكن تخمين رابطها قبل النشر.
- نص تقرير الموسم نص فقط: الصور تُضاف في حقل **الصور** وحده، لتسري عليها هذه القواعد.

## إضافة مراسل وتعيين مدنه

1. ادخل اللوحة `/admin` بحساب مدير.
2. **المستخدمون** ← **إنشاء جديد**.
3. املأ الاسم الحقيقي والبريد وكلمة مرور مؤقتة.
   - **الاسم الحقيقي والبريد** لا يُنشران أبداً، ولا يراهما إلا المدير وصاحب الحساب. المحرر يرى الاسم المعروض والدور فقط. ويُستحسن بريد لا يحمل الاسم الحقيقي.
   - **البريد** يغيّره المدير وحده.
   - **الاسم المعروض** هو ما يراه الزوار (تحقق منه، كاتب التقرير، تصوير). اتركه فارغاً ليصبح «مراسل سوريا عن قرب في {المدينة}»، أو اختر اسماً مستعاراً.
4. اجعل **الدور** = «مراسل»، واختر مدينته أو مدنه في **المدن المعيّنة**، ثم احفظ.
5. أرسل له رابط `/correspondent/login` وكلمة المرور المؤقتة عبر قناة خاصة.

صفحة `/correspondent` مصمّمة للمراسل على الهاتف. يستطيع فتح `/admin` أيضاً، لكن صلاحياته هناك وهنا محصورة في مدنه:

- يحدّث «حال البلد».
- يؤكّد أن معلومة ما زالت صحيحة.
- يرسل تقرير موسم مع صور، فيذهب للمراجعة قبل النشر.

لإيقاف مراسل: احذف مدنه من **المدن المعيّنة**، أو احذف حسابه. كل تغيير يُسجَّل في سجل التدقيق.

بعد 5 محاولات دخول خاطئة يتوقف دخول الحساب ربع ساعة. الرسالة عندها هي نفسها رسالة كلمة السر الخاطئة، حتى لا تكشف أن البريد مسجّل. فك القفل قبل ذلك للمدير وحده.

## النسخ الاحتياطي والاستعادة

النسخ منطقي: كل جدول يُحفظ صفوفاً مع قائمة الـ migrations المطبّقة. السبب أن `pg_dump` المحلي (Postgres 17) لا يقبل خادم Neon (Postgres 18). المنطق في `src/data/backup.ts`.

نسخة من قاعدة الإنتاج، بملف `.env.production.local` (الاتصال المباشر):

```bash
npm run backup -- .env.production.local
```

تُحفظ في `backups/` (مستثناة من git) **مشفّرة فقط** (`.json.gz.gpg`، gpg بتشفير AES-256)، ولا يُكتب أي نص صريح على القرص. السبب أن فيها كل الصفوف، ومنها بصمات كلمات السر والأسماء الحقيقية.

- **كلمة مرور التشفير** في `.env.backup.local` (مستثنى من git). يولّدها أول نسخ تلقائياً دون طباعتها. **احفظ نسخة منها في مدير كلمات المرور:** بدونها لا يمكن قراءة أي نسخة.
- gpg يأتي مع Git for Windows، ويمكن تحديد مساره بالمتغير `GPG`.

استعادة نسخة في قاعدة محلية:

```bash
npm run restore -- backups/<الملف>.json.gz.gpg <ملف env فيه DATABASE_URL للهدف>
```

يفك التشفير في الذاكرة بكلمة المرور من `.env.backup.local`.

خطوات الاستعادة:

1. تطبّق الـ migrations على الهدف أولاً، وترفض نسخة أُخذت بقائمة migrations مختلفة.
2. تستبدل كل الصفوف في transaction واحدة.
3. تعيد ضبط العدّادات.
4. تقارن عدد صفوف كل جدول.

ترفض أي هدف غير محلي ما لم يُمرَّر `--allow-remote` صراحة، لأنها تمسح كل ما فيه.

تجربة الاستعادة (نسخ، ثم استعادة في Postgres محلي مؤقت، ثم مقارنة). تُكرَّر بعد كل تغيير في المخطط، ومرة في الشهر على الأقل:

```bash
npm run backup:drill -- .env.production.local
```

التجربة تستعيد من **الملف المشفّر نفسه** بعد فك تشفيره، لا من الذاكرة، فتُثبت أن النسخة على القرص قابلة للقراءة.

**آخر تجربة على الإنتاج: 2026-10-19 (مشفّرة).** 42 جدولاً، 13 منها فيها بيانات، وتطابقت أعداد كل الجداول.

**ما لا يشمله النسخ:** ملفات الصور على Vercel Blob. خط الدفاع الثاني للقاعدة هو استعادة Neon اللحظية خلال 6 ساعات (الخطة المجانية).

## الخط

IBM Plex Sans Arabic (رخصة OFL) مستضاف ذاتياً ومقصوص إلى:

- الحروف العربية.
- الأرقام العربية والهندية.
- علامات الترقيم العربية.
- اللاتينية الأساسية.

ملفات الخط في `public/fonts`، ونسخ صور المشاركة في `src/og/fonts`. لإعادة القصّ:

```bash
npm run fonts:subset
```

الاختبار `tests/unit/font-coverage.test.ts` يفشل إن استُخدم في النصوص حرف غير موجود في الخط المقصوص.
